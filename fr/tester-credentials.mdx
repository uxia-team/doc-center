Certaines tâches ne peuvent pas être réalisées depuis une page publique. Si votre flux commence derrière une connexion, exige un numéro client pour retrouver une commande ou demande une pièce d'identité au moment du paiement, les participants IA ont besoin de ces valeurs pour aller jusqu'au bout.

Il existe deux façons de tester derrière une connexion :

- **Identifiants.** Vous les ajoutez une fois à un bloc de tâche, et les participants IA les utilisent pour se connecter et pour remplir tout champ demandé par le flux.
- **[Session de connexion interactive](#session-de-connexion-interactive).** Vous vous connectez vous-même dans l'interface d'Uxia. Nous capturons la session connectée : nous ne stockons donc aucun identifiant.

<Note>
  Les identifiants sont disponibles sur les tâches de site web en production et de prototype Figma. Sous l'URL, cliquez sur **+ Add credentials**. Une fois les identifiants enregistrés, le bouton affiche **Credentials added**.
</Note>

## Choisir un mode

La fenêtre **Credentials** s'ouvre sur un choix de **Mode** :

| Mode | Fonctionnement | À utiliser quand |
|---|---|---|
| **Account per tester** (par défaut) | Ajoutez un compte pour chaque participant afin qu'ils naviguent indépendamment. S'il y a moins de comptes que de participants, les comptes sont répartis entre les participants et réutilisés de façon aléatoire. | Le flux écrit des données : paniers, réservations, paramètres. |
| **Shared account** | Tous les participants utilisent les mêmes identifiants. Plus rapide à configurer, mais les sessions peuvent entrer en conflit. | Le flux ne fait que lire des données, ou vous n'avez qu'un seul compte de test. |
| **Integration** | Utilisez un identifiant réutilisable configuré pour ce site web. | Votre organisation dispose d'une intégration pour ce site web. |

**Integration** n'apparaît que lorsque l'URL correspond à une intégration configurée pour votre organisation, et ce mode est alors sélectionné par défaut. L'équipe Uxia configure les intégrations : contactez-nous pour en ajouter une. Une fois ce mode sélectionné, laissez **Activate integration for this test** activé et choisissez un **Credential**, ou cliquez sur **Add credential** pour en enregistrer un nouveau.

## Remplir le tableau

Pour **Account per tester** et **Shared account**, vous saisissez les identifiants dans un tableau :

- **Les colonnes sont des champs.** Le tableau commence par **Username or email** et **Password**. Cliquez sur **Add new column** pour ajouter un champ, saisissez son nom et appuyez sur Entrée.
- **Les lignes sont des comptes.** En mode **Account per tester**, chaque ligne est un compte (**Account 1**, **Account 2**, et ainsi de suite). Cliquez sur **Add new row** pour en ajouter un autre. En mode **Shared account**, une seule ligne s'applique à **All testers**.
- **Supprimez** une colonne ou une ligne avec son icône de corbeille.
- **Les colonnes de mot de passe** sont masquées pendant la saisie. Cliquez sur l'icône en forme d'œil pour afficher une valeur.

Sous le tableau, un compteur indique combien de comptes sont complets. Pour enregistrer, remplissez tous les champs d'au moins un compte, et complétez ou supprimez les lignes partiellement remplies.

## Ce que vous pouvez ajouter

Un identifiant est une valeur étiquetée que les participants IA peuvent utiliser pendant la session. **Il n'existe pas de liste fixe de types de champs** : vous ajoutez tout ce dont le flux a besoin, avec l'étiquette et la valeur de votre choix.

| Champ | Exemple |
|---|---|
| E-mail | `qa-tester@yourcompany.com` |
| Mot de passe | Le mot de passe de ce compte de test |
| Numéro d'identité ou de document | Identifiant de test, numéro d'adhérent |
| Numéro de compte | Numéro de compte de test, référence client, numéro de commande |
| Code | Code de réduction, code d'invitation, code de parrainage |
| Tout autre champ | Tout texte ou nombre demandé par un formulaire de votre flux |

Donnez à chaque colonne un nom clair. Les participants IA s'en servent pour décider quelle valeur va dans quel champ : `Booking reference` fonctionne mieux que `field3`.

## Comment Uxia traite vos identifiants

Les identifiants sont l'élément le plus sensible que vous puissiez placer dans un test : ils sont donc traités différemment du reste du contenu de votre test.

### Chiffrés en transit et au repos

Les identifiants transitent via TLS et sont stockés chiffrés au repos. Ils restent rattachés au bloc de tâche auquel vous les avez ajoutés, pour que vous puissiez relancer le test sans les saisir à nouveau. Ils ne sont déchiffrés que lorsque vous les modifiez ou lorsqu'une session en a besoin.

Les identifiants d'intégration sont chiffrés à l'enregistrement et ne peuvent plus être consultés ensuite.

### Utilisés uniquement pour réaliser le flux

Les valeurs des identifiants ne sont jamais incluses dans les instructions envoyées au modèle d'IA qui pilote le participant. Lorsqu'une session atteint une connexion ou une autre étape protégée, les identifiants sont injectés de façon sécurisée dans la session du navigateur et saisis directement dans les champs correspondants. Le modèle d'IA ne les voit jamais : ils ne peuvent donc pas apparaître dans les commentaires du participant.

Les transcriptions et les captures d'écran montrent ce que les participants ont saisi, comme sur n'importe quel écran : les champs de mot de passe restent masqués, mais un nom d'utilisateur, un e-mail ou un numéro de compte peut être visible. Si vous [rendez vos résultats publics](/fr/share-and-export), toute personne disposant du lien peut aussi voir ces transcriptions. C'est une raison de plus d'utiliser des [comptes de test](#bonnes-pratiques).

### Jamais utilisés pour l'entraînement

Rien de ce que vous soumettez à Uxia n'est utilisé pour entraîner ou affiner un modèle, que ce soit pour Uxia ou pour un tiers. Consultez [Confidentialité des données](/fr/account/security/data-privacy).

### Limités à votre espace de travail

Les identifiants appartiennent au test auquel ils ont été ajoutés, dans votre espace de travail. Seuls vous et les coéquipiers que vous avez invités dans cet espace de travail peuvent les voir : jamais d'autres organisations, ni d'autres clients d'Uxia.

Si vous retirez quelqu'un de l'espace de travail, cette personne perd l'accès au test, et donc à ses identifiants.

<Warning>
  Considérez l'appartenance à l'espace de travail comme la limite d'accès. Toute personne qui peut ouvrir un test peut voir les identifiants qu'il contient : n'invitez donc que des coéquipiers qui doivent disposer de ce niveau d'accès.
</Warning>

## Bonnes pratiques

Même avec ces protections, l'identifiant le plus sûr est celui qui ne peut causer aucun dommage s'il est utilisé à mauvais escient.

<Steps>
  <Step title="Utilisez des comptes de test dédiés">
    Créez des comptes qui n'existent que pour les tests. N'utilisez jamais votre compte personnel, un compte administrateur ou un compte appartenant à un vrai client.
  </Step>
  <Step title="Privilégiez un environnement de recette ou un bac à sable">
    Si vous disposez d'un environnement hors production qui reproduit le flux, testez-y. Cela élimine le risque que les participants créent de vraies commandes, envoient de vrais e-mails ou modifient de vrais enregistrements.
  </Step>
  <Step title="Accordez au compte le minimum de droits nécessaires">
    Un participant n'a besoin que de réaliser la tâche. Évitez les comptes dotés de droits d'administration, d'un accès à la facturation ou de la possibilité de supprimer des données.
  </Step>
  <Step title="Utilisez des données fictives dans les champs personnalisés">
    Les numéros d'identité, de compte et de document doivent être des valeurs de test, pas les données d'une personne réelle.
  </Step>
  <Step title="Ne saisissez pas d'identifiants sensibles ou dangereux">
    Ne saisissez jamais d'identifiants qui pourraient causer un préjudice s'ils étaient divulgués ou utilisés à mauvais escient.
  </Step>
  <Step title="Changez les identifiants après le test">
    Modifiez le mot de passe immédiatement après la fin du test.
  </Step>
</Steps>

<Warning>
  Évitez les comptes protégés par 2FA ou par des codes à usage unique. Les participants IA ne peuvent pas récupérer un code sur un appareil externe ou dans une boîte de réception, et la session reste bloquée à l'étape de vérification. Pour tester ces comptes, utilisez une [session de connexion interactive](#session-de-connexion-interactive). Consultez [Flux que les participants IA ne peuvent pas réaliser](/fr/unsupported-flows).
</Warning>

## Session de connexion interactive

Au lieu de saisir des identifiants, vous pouvez préparer vous-même l'état du test. Vous vous connectez à votre site web via l'interface d'Uxia, et nous capturons la session connectée. Nous ne stockons aucun identifiant.

<Note>
  Les sessions de connexion interactives sont disponibles sur les tâches de site web en production. Si le navigateur interactif n'apparaît pas lorsque vous ajoutez un lien, contactez-nous pour l'activer.
</Note>

<Steps>
  <Step title="Ouvrez le site web dans la fenêtre de lien">
    Ajoutez votre URL à une tâche de site web en production. Le site web s'ouvre dans un navigateur interactif.
  </Step>
  <Step title="Connectez-vous et allez sur la page de départ">
    Allez sur la page où les participants IA doivent commencer, en vous connectant au passage. La connexion Google et le SSO fonctionnent aussi.
  </Step>
  <Step title="Enregistrez">
    Cliquez sur **Save**. Uxia capture la session connectée et la chiffre.
  </Step>
  <Step title="Lancez le test">
    Lancez le test dans l'heure qui suit l'enregistrement. Si la session a expiré, connectez-vous et retournez sur la page de départ.
  </Step>
</Steps>

Tous les participants IA du test utilisent cette session connectée : ils partent donc tous du même état. Utilisez cette méthode pour les flux qui ne font que lire des données, car les participants partagent un même compte. Uxia supprime automatiquement la session une heure après son enregistrement : les participants IA doivent donc commencer dans ce délai. Si vous copiez un test, refaites cette configuration dans la copie.
