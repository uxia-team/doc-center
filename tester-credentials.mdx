Some tasks can't be completed from a public page. If your flow starts behind a login, requires a customer number to look up an order, or asks for an ID at checkout, AI participants need those values to get through it.

That's what **credentials** are for. You add them once to a Task block, and AI participants use them to sign in and to fill any field the flow asks for.

<Note>
  Credentials are available on live website and Figma prototype tasks. Under the URL, click **+ Add credentials**. Once saved, the button reads **Credentials added**.
</Note>

## Choose a mode

The **Credentials** modal opens with a choice of **Mode**:

| Mode | How it works | Use it when |
|---|---|---|
| **Account per tester** (default) | Add an account for each participant so they navigate independently. If there are fewer accounts than participants, the accounts are assigned across participants and reused randomly. | The flow writes data: carts, bookings, settings. |
| **Shared account** | All participants use the same credentials. Faster to set up, but sessions may conflict. | The flow only reads data, or you have a single test account. |
| **Integration** | Use a reusable credential configured for this website. | Your organization has an integration for this website. |

**Integration** appears only when the URL matches an integration set up for your organization, and it's then selected by default. The Uxia team sets up integrations; contact us to add one. With the mode selected, keep **Activate integration for this test** on and choose a **Credential**, or click **Add credential** to save a new one.

## Fill in the table

For **Account per tester** and **Shared account**, you enter credentials in a table:

- **Columns are fields.** The table starts with **Username or email** and **Password**. Click **Add new column** to add a field, type its name, and press Enter.
- **Rows are accounts.** In **Account per tester**, each row is an account (**Account 1**, **Account 2**, and so on). Click **Add new row** for another one. In **Shared account**, a single row applies to **All testers**.
- **Remove** a column or a row with its trash icon.
- **Password columns** are hidden as you type. Click the eye icon to show a value.

Below the table, a counter shows how many accounts are complete. To save, fill in every field of at least one account, and complete or remove any partly filled rows.

## What you can add

A credential is a labeled value that AI participants can use during the run. **There is no fixed list of field types**: you add whatever the flow requires, with the label and value you choose.

| Field | Example |
|---|---|
| Email | `qa-tester@yourcompany.com` |
| Password | The password for that test account |
| ID or document number | National ID, passport, member number |
| Account number | Bank account, customer reference, order ID |
| Code | Discount code, invite code, referral code |
| Anything else | Any text or number a form in your flow asks for |

Give each column a clear name. AI participants use it to decide which value belongs in which input, so `Booking reference` works better than `field3`.

## How Uxia handles your credentials

Credentials are the most sensitive thing you can put into a test, so they're handled differently from the rest of your test content.

### Encrypted in transit and at rest

Credentials travel over TLS and are stored encrypted at rest. They stay attached to the Task block you added them to, so you can re-run the test without entering them again. They're decrypted only when you edit them or when a session needs them.

Integration credentials are encrypted when saved and can't be viewed again.

### Used only to complete the flow

To log in, an AI participant needs to know the values it types. Credential values are therefore included in the instructions sent to the AI model that operates the participant during the session, and they're used only to fill in the matching fields. Participants are instructed never to repeat credentials in their comments.

Transcripts and screenshots show what participants typed, as on any screen: password fields stay hidden, but a username, email, or account number can be visible. If you [make your results public](/share-and-export), anyone with the link can see those transcripts too. This is one more reason to use [test accounts](#best-practices).

### Never used for training

Nothing you submit to Uxia is used to train or fine-tune any model, for Uxia or for any third party. See [Data privacy](/account/security/data-privacy).

### Scoped to your workspace

Credentials belong to the test they were added to, inside your workspace. Only you and the teammates you've invited to that workspace can see them: never other organizations, and never other Uxia customers.

If you remove someone from the workspace, they lose access to the test and its credentials with it.

<Warning>
  Treat workspace membership as the access boundary. Anyone who can open a test can see the credentials on it, so only invite teammates who should have that level of access.
</Warning>

## Best practices

Even with these protections, the safest credential is one that can't do damage if it's misused.

<Steps>
  <Step title="Use dedicated test accounts">
    Create accounts that exist only for testing. Never use your personal account, an admin account, or an account that belongs to a real customer.
  </Step>
  <Step title="Prefer a staging or sandbox environment">
    If you have a non-production environment that mirrors the flow, test there. It removes the risk of participants creating real orders, sending real emails, or changing real records.
  </Step>
  <Step title="Give the account the minimum permissions it needs">
    A participant only needs to complete the task. Avoid accounts with admin rights, billing access, or the ability to delete data.
  </Step>
  <Step title="Use fake data in custom fields">
    IDs, account numbers, and document numbers should be test values, not a real person's data.
  </Step>
  <Step title="Rotate credentials after the test">
    If your security policy requires it, change the password once the run is complete.
  </Step>
</Steps>

<Warning>
  Avoid accounts protected by 2FA or one-time codes. AI participants can't retrieve a code from an external device or inbox, and the session stalls at the verification step. See [Flows AI participants can't complete](/unsupported-flows).
</Warning>
