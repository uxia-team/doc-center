Some missions can't be completed from a public page. If your flow starts behind a login, requires a customer number to look up an order, or asks for an ID at checkout, AI testers need those values to get through it.

That's what **credentials** are for. You add them once when creating the test, and testers use them to authenticate and to fill any field the flow requires.

<Note>
  Credentials are available on **Live source** tests, under **Advanced settings → Credentials & custom fields**.
</Note>

## Shared vs. dedicated accounts

When the flow needs a login, choose how accounts are distributed across testers:

<CardGroup cols={2}>
  <Card title="Dedicated per tester" icon="users">
    Each AI participant gets its own account. Testers navigate independently with no session conflicts. **Recommended** for any flow that writes data — carts, bookings, settings.
  </Card>

  <Card title="Shared account" icon="user">
    All participants log in with the same account. Faster to set up, but testers may collide mid-session and affect each other's results.
  </Card>
</CardGroup>

## What you can add

A credential is just a labelled value the tester can use during the run. **There is no fixed list of field types** — you define whatever the flow requires, with the label and the value you choose.

These are some of the most common ones, but they're only examples:

| Field type | Example |
| --- | --- |
| Email | `qa-tester@yourcompany.com` |
| Password | The password for that test account |
| ID or document number | National ID, passport, member number |
| Account number | Bank account, customer reference, order ID |
| Code | Discount code, invite code, referral code |
| Anything else | Any text or number a form on your flow asks for |

Use **Add field** to create as many custom fields as you need. Give each one a clear label — testers use the label to decide which value belongs in which input, so `Booking reference` works better than `field3`.

## How Uxia handles your credentials

Credentials are the most sensitive thing you can put into a test, so they are handled differently from the rest of your test content.

### Encrypted in transit and at rest

Credentials travel over TLS and are stored encrypted at rest. They stay attached to the test you created them in, so you can re-run that test without re-entering them, and they are decrypted only at the moment a tester session needs to use them.

### Never exposed to the AI model

This is the important one. Credential values are **never placed in the model's prompt or context**.

The AI tester reasons about the page in terms of the *field*, not the *value* — it decides "type the email into this input" and the value is injected directly into the browser at that step. The model never reads it, never reasons about it, and never writes it into its own output.

As a result, credential values cannot leak into session transcripts, insights, or reports.

### Never used for training

Nothing you submit to Uxia is used to train or fine-tune any model, for Uxia or for any third party. Credentials are excluded from this by design, since they never reach a model in the first place.

### Scoped to your workspace

Credentials belong to the test they were created in, inside your workspace. They are visible only to you and the teammates you have explicitly invited to that workspace — never to other organizations, and never to other Uxia customers.

If you remove someone from the workspace, they lose access to the test and its credentials along with it.

<Warning>
  Treat workspace membership as the access boundary. Anyone who can open a test can see the credentials configured on it, so only invite teammates who should have that level of access.
</Warning>

## Best practices

Even with the protections above, the safest credential is one that can't do damage if it's misused.

<Steps>
  <Step title="Use dedicated test accounts">
    Create accounts that exist specifically for testing. Never use your own personal account, an admin account, or an account belonging to a real customer.
  </Step>
  <Step title="Prefer a staging or sandbox environment">
    If you have a non-production environment that mirrors the flow, test there. It removes the risk of testers creating real orders, sending real emails, or modifying real records.
  </Step>
  <Step title="Give the account the minimum permissions it needs">
    A tester only needs to complete the mission. Avoid accounts with admin rights, billing access, or the ability to delete data.
  </Step>
  <Step title="Use fake data in custom fields">
    IDs, account numbers, and document numbers should be test values, not a real person's data.
  </Step>
  <Step title="Rotate credentials after the test">
    If your security policy requires it, change the password once the run is complete. You can update the stored values on the test at any time.
  </Step>
</Steps>

<Warning>
  Avoid accounts protected by 2FA or one-time codes. AI testers cannot retrieve a code from an external device or inbox, and the session will stall at the verification step.
</Warning>
